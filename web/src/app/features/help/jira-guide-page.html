Keeping boards current from Jira

How the Jira connection works, what it will and won't change on a board, and the steps for setting it up and using it day to day.

The short version

A board can be pointed at a Jira project. The app then reads that project's issues and works out three things: which sprint is active, how far along the work is, and whether the squad looks on track.

It reads Jira and nothing more — it never creates, edits, transitions or comments on an issue. Everything flows one way, from Jira into the board.

The important design decision is what happens next. By default the app shows you what Jira says and waits. A Product Owner looks at the numbers and decides whether to take them. Nothing is written to a board until a person agrees, unless an admin has deliberately turned that requirement off.

Two modes

One switch on the settings screen decides how updates arrive. Pick it once; it applies to every linked board.

Default

Suggest only

Jira is consulted when someone opens a board and presses Sync from Jira. The pulled figures appear beside the current ones, with a short reason. The PO presses Apply to draft, then Save — two deliberate steps. Nothing changes on its own.

Opt in

Apply automatically

A background job checks Jira every few minutes and writes sprint, progress and status straight to every linked board. Good for a large portfolio where chasing people for updates is the real cost; it does mean figures can change under a reader without anyone pressing anything.

Recommendation

Start in suggest-only for a sprint or two. It shows you whether the numbers Jira produces actually match how your squads describe themselves, before you let those numbers write to a board unattended.

Admin setup Admin only

Done once for the whole organisation, on the @if (isAdmin()) { Jira settings screen } @else { Jira settings screen }. Everything there acts on behalf of every squad, so it is restricted to administrators.

1. Create a service account and token

In Jira, use a service account rather than your own login. When a person leaves the company their token is revoked, and every board would quietly stop updating. The account needs only Browse projects on the projects you want on the board.

Signed in as that account, go to id.atlassian.com → Security → API tokens and create one. Copy it — Atlassian shows it once.

2. Fill in the connection

Jira URL
Your Jira site, for example https://yourcompany.atlassian.net. It must be https; the form refuses anything else, because a token sent over plain http can be read in transit.
Account email
The service account's email address.
API token
The token from step 1. Once saved it is never shown again — the screen displays only a mask and the last four characters, enough to tell which token is in place.
Enable the connection
Off means no call is made to Jira at all, whatever else is filled in.

3. Prove it works

Enter a project key and press Test connection. This makes a real call, so it can tell three situations apart that otherwise look identical:

What it says What it means
Not configured The connection is off or incomplete. Nothing has been tried.
Configured but returned nothing Jira was reached but gave back no issues — usually a wrong project key, an account without Browse projects, or a revoked token.
Connected, read n issues Working. The count is proof it actually read the project.

4. Choose the mode

Leave Apply Jira figures automatically off to stay in suggest-only. Turning it on reveals the interval — how often the background job checks, from 5 minutes to 24 hours. Changing the interval takes effect without restarting anything.

If the fields are greyed out

Your infrastructure team can pin the credentials as server environment variables, which deliberately outrank the settings screen. When that is the case the form goes read-only and says so — the connection is managed outside the app, on purpose, so that an application admin cannot repoint it.

Linking a board

Done per board, by anyone who can edit it. A board with no project key is ignored by every sync, so you can link squads gradually.

Open the board and find the Jira link card in the builder:

Project key
The short prefix on the squad's issues — the PIRT in PIRT-482. This is the only field the sync needs.
Board id
Optional, stored for future use. The number in a Jira board URL. Leave it blank if you don't know it.

These can be filled in before the connection is switched on, so boards can be prepared in advance and start pulling the moment an admin connects Jira.

Using a suggestion Product Owner

This is the day-to-day flow in suggest-only mode, and it stays available even when automatic updates are on.

  1. 1
    Press Sync from Jira

    On the board editor. The app queries the linked project.

  2. 2
    Read the comparison

    Current progress against suggested, current status against suggested, the done and blocked counts behind them, and the active sprint. A one-line reason explains the verdict — for example "2 of 11 issues are blocked."

  3. 3
    Apply to draft, or dismiss

    Applying only fills the form. Nothing has been saved yet, and you can still edit any field — including overriding the status Jira suggested.

  4. 4
    Save

    Now the board changes, and the change is recorded under your name.

Why two steps

Jira knows about tickets; it doesn't know that the vendor confirmed a slip on a call this morning. The suggestion is evidence, not a verdict — the PO stays the author of the board.

How figures are read

The rules are deliberately simple, so that a number on a board can always be explained to the person it describes.

Each sync asks Jira for the linked project's issues, most recently updated first, up to 200 of them. From those it derives three values.

Progress

The share of issues Jira itself files under the Done status category, rounded to a whole percent. It follows your own workflow — whatever your board treats as done is what counts here.

Sprint

The name of the active sprint on the issues. If it can't be found, the board keeps the sprint it already has: not finding a sprint is ignorance, not evidence the squad has none.

Status

An issue counts as blocked when its status name contains "blocked" — so Blocked, Blocked – vendor and External block all count. The first rule that matches wins, reading top to bottom:

Two consequences worth knowing. Blocked outranks finished — a project that is 100% done but still carries a blocked ticket reads as at risk, not delivered, because the blocker is the thing worth discussing. And In Review is never suggested; it describes a stage of your delivery process that Jira issue states don't reliably indicate, so it stays a human choice.

The mapping errs on the pessimistic side by design. A suggestion that over-reports health is worse than one a PO has to correct upward.

The scheduled run

Only relevant when automatic updates are switched on. With them off, this job wakes up, sees the switch, and goes back to sleep.

  • It starts about half a minute after the API starts, then checks once a minute whether the interval has elapsed.
  • Each run walks every board that has a project key. Boards without one are skipped entirely.
  • A project that can't be reached is reported and the run carries on — one broken project never stops the others.
  • A board whose figures haven't changed is left completely alone: no save, no audit entry, no notification to people viewing it.

An admin can also press Sync now to run it immediately. That is an explicit instruction, so it writes to boards even when automatic updates are off, and the changes are recorded under the admin's own name rather than as an automated run.

Every change lands in the board's audit trail with the old and new value, so you can always see where a figure came from. Scheduled runs are attributed to Jira sync; a manual Sync now carries the admin's name; an accepted suggestion carries the Product Owner's.

That distinction matters in a status meeting. "Progress went 40 → 65, Jira sync, Tuesday 09:14" answers a question that "it says 65" does not.

The API token

The token lets the app read your company's Jira, so it is treated as a credential rather than a setting.

  • It is encrypted before it is stored, and never written to the database in plain text.
  • It is never sent back to a browser. The screen shows a mask and the last four characters — enough to identify it, not to use it.
  • Leaving the token field blank on a later save keeps the stored one, so changing the interval never means re-pasting the secret.
  • Disconnect removes it entirely.
  • Only administrators can view, change or test the connection.

For whoever deploys this

The encryption keys must be stored somewhere that survives a restart. In a container with no persistent key directory the keys are regenerated on each deploy, and the stored token can no longer be decrypted. The app reports this plainly; the fix is to re-enter the token once keys are persisted.

When it doesn't work

Symptoms in the order they usually come up.

Symptom Likely cause and fix
No Sync from Jira button on the board The connection isn't enabled. An admin sets it up under Settings → Jira.
"This board has no Jira project key" Add the key in the board's Jira link card and save.
"Jira returned nothing for project…" Wrong key, or the service account lacks Browse projects on it, or the token was revoked. Test the connection with that key to narrow it down.
Progress updates but the sprint never does Sprint lives in a custom field whose identifier differs between Jira sites, and yours isn't the common default. Progress and status are unaffected; set the sprint by hand, and ask your Jira admin for the sprint field id.
Boards aren't updating on their own Expected unless Apply Jira figures automatically is on. Also check the interval has elapsed and the boards have project keys.
The form won't accept the URL It must start with https://. A token over plain http can be read in transit.
Everything worked, then stopped after a deploy Usually the encryption keys weren't persisted. Re-enter the token; see the note above.
Status looks wrong for the squad Check how your workflow names blocked states, and remember blocked outranks done. A PO can always override the suggestion — that is what the two-step flow is for.

The connection is read-only: this app never writes to your Jira.
